Orchestration

Orchestration, here, means several developers, each directing their own AI agents, working towards one goal: they plan the work, split it, build it in parallel and merge it, through one shared record.

Today, one developer, Andrius, directs one orchestrator: a Claude session that plans the work, sends out agents to do it and checks what they report. That part is how Orion-81 is made, and it works. How two developers could share the project in the same way is a proposal for discussion, not current practice. Each section below says which it is.

The working loop

Every batch of work runs the same seven steps.

  1. Step 1PlanPlanner: items, owners, checks
  2. Step 2ExecuteExecutor: in parallel
  3. Step 3IntegrateExecutor: merge, build, time the tests
  4. Step 4ReviewPlanner: find and judge
  5. Step 5FixExecutor: each finding
  6. Step 6VerifyExecutor: run the checks
  7. Step 7AcceptPlanner: sign off, close

Blue cards are planner work (Claude Opus 5.5). Amber cards are executor work (Claude Sonnet 5.5). Steps 5 and 6 repeat until the review is clean.

Example, 28 October: M2.3's part M was built by an executor, reviewed by two planner-model reviewers, fixed in two rounds and re-checked. It was then merged and its test time checked against the limit Andrius set.

Spec-driven chunks

From Andrius's idea to the main line in four stages.

  1. 1. SpecClean-room writers turn Andrius's ideas into spec text. Lint, isolated scans and sanitisers check it. Andrius signs.Passes on: signed specs, each file pinned by its checksum.
  2. 2. PlanA planner cross-checks the plan against the code it builds on: frozen contracts, work items, file scopes and a test-time budget.Passes on: the cross-check and its tracker items.
  3. 3. BuildWaves of items on the milestone's own integration branch. Each item owns its files. Review, fix, re-check.Passes on: a merged, timed integration branch.
  4. 4. LandThe close: four builds from clean, lint, provenance scans and a planner review. Then the merge into the main line, on Andrius's word.Passes on: a new main line and a version number.

M2.3, end to end: spec batches A2 and B signed on 27 October and ratified by Andrius the next day, then twelve revisions of the cross-checked plan, then parts C and M and wave 4 merged. Its last spec batch, its close and its merge are still to come.

Two developers, one project

Proposal for discussion

Everything in this section describes how two developers, each with an orchestrator, could share Orion-81. It is not how the project runs today. Where a mechanism already works, the table says where.

Rules of engagement: six rules for working side by side

  1. 1. One owner per areaA file has one writer at a time. Every tracker item names its files.
  2. 2. Contracts move by itemInterfaces are frozen in the cross-check. Changing one is a planner item that both sides see.
  3. 3. One merge at a timeMilestones land in the main line in the planned order, each with its full test and review results and Andrius's word.
  4. 4. Re-check firstBefore building, each side cross-checks its plan against the latest main line.
  5. 5. Review each otherAt every close, the other side's fresh planner-model reviewer is the independent read.
  6. 6. One reference clockTest times are binding on one machine only. Every log time comes from the system clock.

Andrius's questions: one queue for both sides, each question with an explainer page checked before it reaches him.

Bringing someone on: a first week that teaches the whole loop

Day one
  • Access to the game repository and the project folder
  • The project's instruction files and the model policy: Claude Opus 5.5 plans and reviews, Claude Sonnet 5.5 builds and tests
  • The clean-room rules: which folders are off limits, and no engine work until the engine question is settled
  • Sessions are recorded by the project hooks, after a privacy check
  • Each developer works from their own Claude account
First week
  • Run one independent review: M2.3's close is real work with low risk
  • Take an id block and a lane of areas, recorded in the tracker
  • Plan their first milestone half, starting with its cross-check

What could go wrong: six risks, each with a safeguard

RiskSafeguard, and where it already shows
Two writers, one fileFile ownership on every item, and one merge into the main line at a time
A contract moves underneathFrozen contracts, and the re-check against the main line before each milestone starts
Test-time budgets collideA test-time ceiling per milestone, set by Andrius, so the later milestones keep room
Andrius becomes the bottleneckOne batched question queue, with a checked page for each question
Outside text slips inClean-room roles kept apart, with lint and provenance scans at every close
Capacity runs outWork pauses at clean checkpoints, as the M2.3 spec batch did on 29 October

The one-line version

Split by contract. Build in parallel. Merge in order. Review each other.

The mechanisms this needs already exist in the tracker, the specs and the branches. A second developer would add a second orchestrator, a second lane and a second pair of eyes.
